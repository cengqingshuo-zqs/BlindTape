### 代码结构

```
data_layer/
  config.py   # 读 config.yaml，所有可调参数集中在这里（过滤门槛、请求间隔、复权方式等）

  pool.py     # 按 config 里的过滤规则算"可训练标的池"，每只ETF都保留一行+拒绝原因，方便人工核对
  cli.py      # 命令行入口：fetch-list / fetch-hist / build-pool / run-all
tests/        # 19个单元测试，全部mock akshare调用，不需要网络也能跑
config.yaml   # 过滤参数、请求参数配置
data/         # SQLite数据库 + 标的池CSV输出（已加入.gitignore，不进仓库）
```

运行方式：
```bash

pip install -r requirements.txt

python -m data_layer.cli fetch-list           # 拉全市场ETF列表

```

### 数据库表结构

- `etf_list`：全市场ETF快照（代码/名称/抓取时的成交额/快照时间），每次 fetch-list 覆盖式更新
- `etf_daily`：逐标的历史日线，主键 `(symbol, trade_date)`，字段对应 akshare `fund_etf_hist_em` 的开高低收/成交量/成交额/振幅/涨跌幅/涨跌额/换手率
- `fetch_state`：每个标的的增量更新状态（`last_trade_date` / 最后抓取时间 / 状态 ok\|error / 错误信息）—— `fetch-hist` 靠这张表决定下次从哪天开始拉，失败的标的下次会自动重新尝试（因为失败时 `last_trade_date` 不会前进）

### 关键设计决策

- **复权方式用前复权（qfq）**：近期价格=真实成交价（分红/拆分只影响历史价格的回溯调整），既不会因为分红造成K线跳空缺口，也不影响用最近收盘价做人工抽查核对。写在 `config.yaml` 的 `adjust` 字段，可调。
- **"上市日期"用本地历史数据里最早一条交易日近似代替**：akshare 的ETF列表接口不直接给上市日期，而ETF从上市第一天起就有日线数据，所以取 `etf_daily` 里该标的最早的 `trade_date` 作为上市日近似值，足够准确。
- **标的池过滤给3个独立可调参数**（都在 `config.yaml` 的 `pool_filter` 下），任何一项不达标都会被剔除，`build-pool` 输出的CSV里每一行都写明具体是哪个/哪些原因被拒（`reject_reason` 列，逗号分隔）：
  - `min_years_listed`（默认2年）：上市时长，用上面的"最早交易日"算
  - `min_avg_amount_yuan` + `amount_lookback_days`（默认500万元 / 最近60个交易日均值）：近期流动性门槛，成交额单位是"元"（akshare原始接口就是元，不是万元，写代码时特意确认过源码）
  - `min_valid_trading_days`（默认480，约等于2年交易日数）：剔除数据缺失严重或历史很短的迷你ETF，和"上市满N年"是两个独立维度（一个看数据长度，一个看数据密度/完整性）
- **增量更新** 靠 `fetch_state.last_trade_date`：有记录就从"最后日期+1天"开始拉，没记录/`--full` 就从 `19700101` 全量拉。请求间加 `random.uniform(sleep_min, sleep_max)` 秒的随机延迟（默认0.5~1s），避免被识别为爬虫。
- **重试**：`fetch.with_retry` 包一层指数退避重试（默认3次），因为 akshare 的 `fund_etf_hist_em` 本身**没有**内置重试（`fund_etf_spot_em` 倒是有，看过源码确认的）。

### 已知问题 / 环境坑（给下一个排查网络问题的人省时间）

- 开发机挂了本地代理（Clash，端口7890）。实测发现 `push2delay.eastmoney.com`（ETF列表快照接口，`fund_etf_spot_em` 用的）比 `push2his.eastmoney.com`（历史日线接口，`fund_etf_hist_em` 用的）**明显更容易触发东财反爬限流**——短时间内多次调试请求（几十次/几分钟）会导致该host返回"TLS握手成功但GET请求后空回复"，代理配置本身没问题，纯粹是被限流，等一段时间/降低请求频率会自动恢复。技术方案文档里其实已经提前预警了这个风险（"偶发东财接口反爬报错"），实测确认属实，脚本里的重试和请求间隔就是为了应对这个。
- 排查过程中一度怀疑是代理路由问题（怀疑该走DIRECT没走），后来确认不是——即使换路由方式，同一个出口IP短时间内被限流的表现是一样的。**结论：不用改代理规则，单纯是请求频率导致的临时限流，冷却后正常。**

## 核心训练引擎（技术方案「开发顺序」第2步）—— 已完成第一版，可用

对应技术方案模块2「随机抽样引擎」+ 模块3「盲测训练前端」里不含UI的核心逻辑部分。

已确认的设计参数（问过用户）：**窗口固定150个交易日**（不是随机区间），跑起来先用 **Jupyter Notebook配合matplotlib画K线**，不做命令行交互版本。

### 代码结构

```
training_engine/
  sampling.py  # sample_window(): 从标的池随机选标的+随机起点，抽固定长度窗口
  engine.py    # TrainingSession: 逐根揭示K线、记录操作、算权益曲线/回撤/收益/在场时间
  export.py    # build_export()/save_json(): 按技术方案的导出结构打包成JSON
notebooks/
  training_engine_demo.ipynb  # 手动跑一遍训练流程的示例（真实数据跑通过）
```

新增 `config.yaml` 的 `sampling` 段：`window_trading_days`(150) / `max_start_search_attempts`(50) / `max_calendar_span_ratio`(1.8，窗口日历天跨度不能明显超过理论交易日跨度，用来剔除中途夹了长期停牌的窗口——数据行是连续的，但日期会跳空一大段）。

### 关键设计决策

- **仓位模型**：只用一个 0~1 的浮点数表示"虚拟资金投入这只标的的比例"，不做真实下单/杠杆/手续费。操作在"当前已揭示的最后一根K线收盘价"执行。
- **收益归因的时序**：第i天的涨跌幅，敞口用的是"第i-1天收盘后已生效的仓位"——也就是说当天收盘做的操作，只影响明天的敞口，不能倒着吃到今天已经走完的涨跌。写了专门的单测覆盖这个边界情况（`tests/test_engine.py::test_action_on_day_i_does_not_affect_day_i_return`），这是最容易写错的地方。
- **导出JSON定了 schema_version="0.1"**，`system_signals` 字段先留 `null` 占位，等模块4（v1.1系统信号复刻）做完再回填，不用改导出结构。

### 踩的坑（记一下，别人也可能踩到）

**pandas读CSV把纯数字的ETF代码列推断成int64**：`tradable_pool.csv` 里的 `symbol` 列全是"159915"这种纯数字字符串，`pd.read_csv()` 不指定dtype的话会自动推断成int64。这个bug很隐蔽——拿int64当symbol去查SQLite的 `etf_daily` 表居然**查得到**数据（SQLite的类型亲和性规则会把TEXT列和INTEGER参数做隐式转换比较），但拿去查 `{symbol: name}` 的Python字典就**查不到**（dict的key匹配是精确类型匹配，int64(159915) != str('159915')），导致 `sample.name` 静默变成空字符串，不报错但结果是错的。

用真实数据跑Jupyter notebook（`jupyter nbconvert --execute`）时才发现——单元测试当时全过是因为测试里都是在同一个Python进程里直接传DataFrame，没有真的走一遍"CSV存盘再读回"这个环节。**教训：涉及标的代码这种"看起来像数字但其实是字符串"的字段，任何一个读取入口（CSV/JSON/用户输入）都要显式转str，不能依赖调用方规矩。**

修复：`sampling.sample_window()` 里选出symbol后立刻 `str()` 强转（防御性修复，不管上游传进来的pool_df是什么dtype都不怕），notebook里读CSV时也加了 `dtype={"symbol": str}`（根治读取入口）。`tests/test_sampling.py::test_sample_window_handles_symbol_column_read_back_as_int64` 是这个bug的回归测试。

## 网页前端（技术方案「开发顺序」第4步）—— 最小可用版本已完成，本地跑通

### API

| 方法+路径 | 作用 | 盲测约束 |
|---|---|---|
| `POST /api/sessions` | 抽样开一个新训练 | 返回值只有session_id和窗口长度，不含标的信息 |
| `POST /api/sessions/{id}/reveal` | 揭示下一根K线 | 返回的bar只有OHLCV，不含日期 |
| `POST /api/sessions/{id}/act` | 执行买/加仓/卖/清仓 | — |
| `POST /api/sessions/{id}/finish` | 结束训练 | — |
| `GET /api/sessions/{id}/answer` | 揭晓真实标的/日期/完整数据 | **后端强制**：`session.finished_at is None` 时返回403，不是靠前端不调用来保证盲测，前端跳过confirm也没法提前偷看 |
| `GET /api/sessions/{id}/export` | 导出训练JSON（同时落盘到`data/sessions/`） | 同上，要求已结束 |

### 关键设计决策

- **盲测约束在后端强制，不依赖前端**：`/answer` 和 `/export` 两个接口检查 `session.finished_at`，没结束训练直接403。这样就算前端有bug或者用户直接用curl戳接口，也不可能在没打完的情况下看到真实标的和日期。
- **K线时间轴**：训练过程中的盲测图表用 `dayIndex * 86400` 这种假的递增时间戳喂给lightweight-charts（库要求每个数据点必须有递增的`time`字段），同时把 `timeScale.visible` 设成 `false` 彻底不显示时间轴，避免用户从坐标轴猜出年份。揭晓页的图表才换成真实的 `"YYYY-MM-DD"` 日期字符串。
- **会话状态存进程内存**：单人自用工具，重启服务就清空所有进行中的训练，可接受，不做持久化（历史训练记录管理是技术方案里"迭代打磨"阶段的事，第6步）。

### 踩的坑

1. **原型里用了 `window.confirm()` 做"结束训练"的确认弹窗，结果这个环境的浏览器自动化工具会静默取消原生confirm弹窗**，导致点了按钮但请求根本没发出去、也没有任何报错——表面上看起来像按钮失效了。用真实浏览器点了几次才揪出来（网络请求列表里完全没有 `/finish` 请求，才确认是confirm被吞了）。原生confirm弹窗本来在手机浏览器上体验也一般，直接去掉了，改成点一下就直接执行——反正是自己练习用的工具，不是什么高风险操作，不需要二次确认。
2. **"开始新一轮训练"复用同一个揭晓图表时，每次都调用 `chart.addSeries()` 创建新的K线/权益曲线/标记点，导致多轮训练后图表上的旧数据一直叠加**（第一轮的K线还留在图上，第二轮的又画一份上去）。修复：K线/权益曲线的 `series` 对象只在第一次创建，之后每轮复用 `series.setData()` 整体替换；操作标记点同理，用 `markersPrimitive.setMarkers()` 替换而不是重新 `createSeriesMarkers()`。这个坑要跑两轮完整训练才能复现，单轮测试完全看不出来。
3. **手动核对数据走不通浏览器人工比对这条路**（见上面"数据质量核查"一节）——不是网页前端本身的坑，但也是这一阶段发现的浏览器沙盒限制，一并记在这。

### 交互细节补充（用户反馈后追加）

跟数据层无关，是网页前端交互体验的4处调整：

1. **训练一进去就先展示100天历史背景K线**（不逐根推进，只是给个走势背景），150天的可操作训练窗口紧接在背景之后完整保留。这需要 `sampling.sample_window()` 额外多拉 `context_days`（默认100，`config.yaml` 的 `sampling.context_days` 可调）天数据，`Sample` 数据类新增 `context_ohlcv` 字段。**注意**：这100天不算训练窗口本身，只是显示不能操作——`TrainingSession`（`engine.py`）完全没变，操作只针对`sample.ohlcv`那150天。
2. ~~仓位改成整数"成"（十分之一）而不是连续百分比~~ —— 这一版的+/-步进器交互已经被下面"参照参考App重做交易交互"整个取代，成/元换算逻辑保留，只是交互形式变了。
3. **买卖点在K线柱上标B/S符号**：买入标红色"B"，卖出/清仓标蓝色"S"，盲测图和揭晓图都有（用lightweight-charts v5的 `createSeriesMarkers()`/`setMarkers()`）。
4. **成本线+最新价线**：`series.createPriceLine()` 画两条横线。成本线是持仓的加权平均成本（前端算的，公式：`新成本=(旧成本*旧仓位+成交价*本次仓位变化)/新仓位`，只在加仓时更新，减仓不变，清仓后成本线消失）；最新价线永远是已知的最后一根收盘价。**这两个计算逻辑目前只写在JS里（`app.js` 的 `computeFinalAvgCost`/`computeMA`），后端没有对应实现**——如果以后要在导出JSON里也带上MA/成本数据，这两个函数需要照抄一份到 `training_engine` 或者干脆前端算完一起传给导出接口，现在导出JSON里没有这些字段。

**踩的坑（这几个改动过程中新发现的）**：
- **`el.reviewOverlay.classList.remove("hidden")` 调用顺序错了会导致图表整个渲染错乱**：一开始是等所有图表数据都setData完了、`fitContent()`调用完了，最后才把复盘弹层从 `display:none` 变成可见。结果K线全挤在图表右侧一小块，大片空白——因为lightweight-charts的 `autoSize:true` 是在图表创建那一刻就去量容器宽度，这时候容器还是 `display:none`（宽度是0），之后即使容器变可见了，图表内部的尺寸缓存也没跟着更新。**修复：把 `classList.remove("hidden")` 挪到创建/更新图表数据之前**，让容器先有正常宽度，图表才能量对尺寸。这个坑只有在图内容占满整个时间跨度（比如这次新加的100天背景+150天窗口=250天）时才会看得明显，之前测试时数据量不够大没发现。

### 参照参考App重做交易交互（用户给了截图参考）

用户发了一个类似的"K线训练"App截图（爆竹K线训练），要求照那个交互模式改，四点具体要求：

1. **买卖仓位改成"目标仓位"点选菜单，不是加/减步进器**：点"买入"从按钮上方弹出菜单，列出比当前仓位高的所有目标档位（比如当前6成，弹"加至满仓/加至9/10仓/加至8/10仓/加至7/10仓"）；点"卖出"弹出比当前低的档位+清仓（"清仓/减至5/10仓/.../减至1/10仓"）。点哪个就直接把仓位设到那个目标值，不是叠加。原来的 `-`/`+` 步进器和"买入/加仓/减仓/清仓"四按钮布局整个换掉了。
2. **MA最多同时显示4条**：`training.default_ma_periods` 从单个 `int` 改成长度4的 `list[int]`（默认 `[5, 20, 0, 0]`，0表示这一条不启用），页面上4个MA周期输入框，每条配一个固定颜色（黄/橙/青/紫），盲测图和揭晓图各自维护4条 `LineSeries`。
3. **一进训练就看到第一根K线，不用先点一下"下一根"**：`startNewSession()` 里创建完session之后自动调一次 `revealNext()`。
4. **原来的"推进下一根"按钮拆掉了，改成买/卖操作自带推进**：现在没有单独的"下一根"按钮——买入菜单选完一个目标仓位、或者卖出菜单选完、或者点中间的"观望/持有"按钮，都会在执行完仓位调整后自动调用 `revealNext()` 推进到下一根。中间按钮文案跟着当前仓位是否>0在"观望"（空仓时）/"持有"（有仓位时）之间切换，纯粹是"不调整仓位、直接推进"的快捷方式。"结束训练/揭晓"单独挪到了顶部状态栏右上角，变成一个不起眼的小链接按钮，因为新的三按钮布局（买入/观望-持有/卖出）已经占满了操作区。

技术上：后端 `act()` 接口完全没变（还是"action + 相对delta"的语义），前端算好 `delta = 目标仓位 - 当前仓位` 再决定传 `buy`（正）还是 `sell`（负）还是 `liquidate`（目标是0，这种情况直接走liquidate分支忽略delta大小，跟原来的引擎逻辑对得上）。`training_engine/engine.py` 的 "add" 动作类型还留着（没删，Jupyter notebook那条路径还在用），只是网页前端不再发这个动作了。

真机验证：本地dev server里完整跑了一轮（买入6成->推进到底->揭晓），菜单弹出的选项、点选后的仓位/推进都跟截图里的参考App行为一致；3条MA同时显示测试过（5/20/60三色都对）；手机视口（375×812）状态栏文字之前换行，调整过文案和CSS `flex-wrap` 后单行显示正常。
